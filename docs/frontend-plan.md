## 0. 一句话定位

一个 **不限年龄** 的英语学习产品：学习者端是一张看得见进度、每次答对都有回响的
**训练场地图**；监护人端是一个**只讲事实的周报**。同一套产品语言，按内容分层适配 4 岁到成人。

**产品不做年龄准入，只做内容分层。** 4–7 是首发主档，7–12、13–16、17+（商务/考试）后续
按同一套骨架扩展——页面不增不减，变的是题型配比、词汇量、单题时长与界面密度。

| 角色 | 要什么 | 不要什么 |
| --- | --- | --- |
| 学习者 | 今天从哪继续、点一下就出声、答对有奖励 | 菜单、长说明、被当小孩 |
| 监护人 | 到底学没学到、每天多久、哪里薄弱 | 公开排名、游戏化炫耀 |

**核心循环**：今日任务 → 地图闯关 → 即时奖励 → 复习 → 学习周报。

## 2. 第 4 点详解：界面语言怎么做

这不是「中文还是英文」一句话的事，它同时决定了**谁来读**、**字号多大**、**孩子要不要认字**。
三种做法：

### A. 纯中文界面（推荐先做这个）

家长端、学习端都用中文写，英文只出现在**要学的内容**里（单词、句子、发音）。

- 学习端：「听一听，选出正确的图」「再试一次」「第 4 关 · 数字」
- 英文只在这里：`Numbers`、`apple`、`I like apples.`

好处：4–7 岁还不识字也能用（靠图标 + 语音），对中文母语用户零门槛，做起来最快。
代价：成人档（17+）看到「再试一次」这种语气会觉得被当小孩——但成人档本来就该换语气，
这是 §3 内容分层要解决的问题，不是加英文能解决的。

### B. 中英双语界面（学习端中英并排，家长端中文）

每个界面文案下面挂一行英文：`再试一次 / Try again`。

好处：有英语环境感，成人档可以直接切纯英文。
代价：**双倍文案**，4–7 岁屏幕上的字会翻倍，挤压图片空间；中文用户的眼睛会自动忽略英文那行。
实际上「双语并排」在小屏上通常是负担而不是帮助。

### C. 全英文界面

对 4–7 岁风险最大：孩子不认识字，连「退出」都找不到。不建议首发用。

### 我的建议

**A 为主，B 作为成人档的开关，C 不做。**

具体落到页面：

1. 学习端界面语言**跟随内容档**，不跟用户手选：
   - 4–7 / 7–12：中文界面 + 英文内容（方案 A）
   - 13–16：中文界面 + 英文内容，但语气改为平级（「不对，再看看」而非「再试一次」）
   - 17+：**英文界面**（方案 C 只在这里出现），配一个小开关可切回中文
2. 家长端/监护端：永远中文。
3. 技术上做成**文案字典 + `locale` 字段**：页面里不写死中文，所有文案走 `t('unit.tryAgain')`，
   内容档带 `locale`，成人档切 `en` 就给英文文案。这一层不加页面，只加一个 `i18n/` 目录，
   后期要加别的语种也不用改页面。

**一句话**：现在按中文界面做，但所有文案走字典，别写死在 JSX 里——这样 17+ 的英文界面后面
只是加一份字典的事，不用返工。

## 3. 内容分层（替代「年龄」约束）

**页面不随年龄变，内容档变。** 每个课程/单元带一个 `level`，页面按它调整密度与语气。

| 内容档 | 适用 | 界面密度 | 题型配比 | 单题时长 | 语气 |
| --- | --- | --- | --- | --- | --- |
| `kids-a` | 4–7（首发） | 大图少字，触控 ≥200px | 听音选图 60% · 跟读 25% · 点读 15% | 5–10s | 鼓励式「Great!」 |
| `kids-b` | 7–12 | 中图，可加短句阅读 | 听音选图 35% · 拼读 25% · 阅读 25% · 跟读 15% | 10–20s | 鼓励式，减少夸张 |
| `teen` | 13–16 | 文字为主，可加长句 | 阅读 40% · 语法 25% · 听力 25% · 口语 10% | 20–40s | 平级「Not quite, try again」 |
| `adult` | 17+ / 商务 | 信息密，可表格化 | 阅读 · 商务场景对话 · 写作纠错 | 30–90s | 商务中性「Review this sentence」 |

同一套路由、同一套组件，靠 `level` 决定：图卡尺寸、每屏题数、是否显示文字、
提示语措辞、是否出现「吉祥物」。**吉祥物在孩子档出现，成人档隐藏**——这是 `level` 控制的，
不是另做一套页面。

「学习地图」在成人档依然成立（课程路径本来就长这样），只是节点变小、路径更直。

## 5. 内容来源与前端接口

两条线并行，前端只看统一的数据形状，不关心内容是生成的还是引入的。

### 5.1 自建：Dify + API 生成分阶段课程

前端消费的是**已经生成好并落库的课程**，不在浏览器里调模型。

```
Dify 工作流（后端侧）
  │  输入：level、主题、词汇量、题型配比
  │  输出：结构化 JSON（单元 + 题目 + 音频文本 + 图片提示）
  ▼
课程服务 API（后端侧）──审核/落库──► 前端
```

前端需要的接口（先按这个契约做 mock）：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/courses?level=kids-a` | 课程列表（`/courses` 页） |
| GET | `/api/courses/:slug` | 课程详情 + 单元列表 |
| GET | `/api/courses/:slug/units/:unitId` | 单个单元的全部题目 |
| GET | `/api/users/me/progress` | 今日任务、当前关、星星、断点 |
| POST | `/api/users/me/sessions` | 一次练习作答上报（批提交） |
| GET | `/api/reports/weekly?week=2026-W45` | 周报数据（图表用） |
| POST | `/api/generate/units` | **仅后台用**：触发 Dify 生成，前端不暴露给终端用户 |

关键约束：

- **生成是异步的**，`POST /api/generate/units` 返回 `jobId`，前端（后台管理页）轮询状态。
  普通学习者页面永远只读已发布内容，不会卡在生成中。
- 每道题必须有 `audioText`（TTS 文本）与 `imagePrompt`（图卡提示词），前端负责播放与兜底图。
- 内容发布前要有人工审核标记 `reviewed: true`，前端只展示已审核单元。

### 5.1.1 Dify 侧要产出什么（给后端/你）

> ✅ **已有实现**：[`web/dify/OU.yml`](../web/dify/OU.yml) —— 基于「deepseek 听写工作流」改造，
> 产出下面这个形状。用法与改动说明见 [`web/dify/README.md`](../web/dify/README.md)。
> 样例产出：[`web/src/lib/sample-ou-course.json`](../web/src/lib/sample-ou-course.json)，
> 转换器：[`web/src/lib/dify-adapter.ts`](../web/src/lib/dify-adapter.ts)。

Dify 工作流输出必须**严格是下面这个形状**，前端只认它：

```jsonc
// 一个单元
{
  "unitId": "kids-a-farm-01",
  "level": "kids-a",
  "topic": "Farm Animals",
  "titleZh": "农场动物",
  "wordCount": 8,
  "estMinutes": 5,
  "questions": [
    {
      "type": "listen_choose_image",       // 见下方题型枚举
      "promptZh": "听一听，选出正确的图",
      "audioText": "cow",                   // 送 TTS
      "options": [
        { "id": "a", "imagePrompt": "a cartoon cow, flat illustration, sky blue background", "correct": true },
        { "id": "b", "imagePrompt": "a cartoon duck, flat illustration, sky blue background", "correct": false }
      ]
    }
  ]
}
```

题型枚举（前端按这个分发组件，新增题型只加枚举值不改页面）：

| `type` | 适用档 | 中间区组件 |
| --- | --- | --- |
| `listen_choose_image` | 全档 | `PictureChoice` |
| `repeat_word` | 全档 | `SpeakCard` + `WaveCanvas` |
| `blend_sounds` | 4–12 | `BlendTiles` |
| `tap_to_read` | 4–12 | `WordCard` |
| `read_choose` | 7–12 起 | `ReadingChoice` |
| `cloze` | 13–16 起 | `ClozeText` |
| `business_scenario` | 17+ | `DialogueCard` |

**Dify 里值得用到的节点**（我查过它的节点清单）：`LLM` 负责出题、`Code` 节点做 JSON 校验与
枚举兜底、`Parameter Extractor` 保证字段齐全、`Iteration` 一次生成一个单元的多个题、
`If-Else` 按 `level` 分流不同题量。生成完一定过一道**结构校验**再落库——
模型漏字段是常态，前端不该为坏数据写防御分支。

图片怎么来：先期用 `imagePrompt` 走统一图库生成（同一套 prompt 前缀保证画风一致），
前端只拿最终 URL；**不要**在浏览器里现生成图片。

**OU 目前只会产出 4 种题型**：`listen_choose_image` / `tap_to_read` / `read_choose` / `cloze`。
`repeat_word`（要录音）、`blend_sounds`（要拼读音频切分）、`business_scenario`（要商务对话）
等前端组件做好后再加进工作流的题型枚举——现在强塞会产出前端渲染不了的题。

**工作流产不出、要后端补的三个字段**（跨端实测发现的缺口）：

| 字段 | 谁补 | 为什么 |
| --- | --- | --- |
| `Unit.index` | 后端 | 第几关属于课程顺序，不属于内容 |
| `Unit.status` | 后端 | `done`/`current`/`locked` 属于学习者进度 |
| `Option.imageUrl` | 后端 | OU 只给 `imagePrompt`，要调图库生成后回填 |

前端对 `imageUrl` 为空已有兜底（几何占位图，按 prompt 哈希取色 + 形状区分，不会白屏）；
`index` / `status` 由 `dify-adapter.ts` 在接入时按顺序临时填充。

### 5.2 引入：第三方内容怎么接

**统一约束（三条，先定死，避免返工）：**

1. 引入内容一律转成 §5.1 同一套 JSON（`unit` / `question` 形状），**页面代码一行不改**。
2. 音频支持两种形态：直接给音频 URL（可直接播），或给文本（走我们自己的 TTS）。前端两者都要处理。
3. 每条内容在 `THIRD_PARTY_NOTICES.md` 的 `content/` 小节登记：来源、许可、抓取日期。
   **许可不明确的一律不用**——这比事后下架便宜得多。

**已核实的接入路线（按风险从低到高）：**

| 来源类型 | 状态 | 说明 |
| --- | --- | --- |
| **公共领域文本**（Project Gutenberg 等） | ✅ 可商用，已验证 | 见下方专门说明，是最安全的第一批内容 |
| 自建 + Dify 生成 | ✅ 主路线 | §5.1，覆盖面最广，可控 |
| 开源分级读物（CC 授权项目） | ⏳ 待逐个核验 | 需逐项目确认 CC 版本、是否允许商用与改编 |
| 商业平台内容（Raz-Kids、Epic 等） | ❌ 不可用 | 授权仅限其平台内使用，不能转授权给第三方产品 |
| 儿歌/韵文（Super Simple Songs 等） | ❌ 慎用 | 音频与曲谱版权独立，标志性曲目维权积极 |

**Project Gutenberg 的许可我已经核对过原文，有一个对商业化很关键的细节：**

> 一本古登堡电子书由两部分组成：**不受美国版权限制的文本** + **古登堡商标与许可声明**。
> 官方原话是：如果你把古登堡许可与所有古登堡提及从文本中剥离，「你就只剩下一份不受美国知识产权法限制的文本」，
> 在美国及世界大部分地区「你可以对它做任何事」。

所以对接方式必须这样做：

- ✅ **下载后剥离 PG 头部与尾部**（`*** START OF THE PROJECT GUTENBERG EBOOK ***` 到 `*** END ***` 之间之外的全部内容），
  只保留正文，然后作为我们自己的内容入库。
- ❌ **不要在产品界面出现 "Project Gutenberg" 字样**。一旦带上这个商标再收费分发，
  就会触发商标条款里的版税义务（毛利润 20%）。
- 剥离正文后按 `level` 重新编排成单元——古登堡原文对 4–7 太深，
  通常只用于 13–16 / 17+ 档的阅读材料，并需要切分、简化、配题。

**结论**：第一批引入内容走公共领域文本（13–16 / 17+ 阅读），4–12 档全部由 Dify 自建。
开源分级读物我继续逐个核验，有明确可商用的会补进这张表。

### 5.3 对页面的影响

只有两处新增：

- `/courses` 增加**筛选器**：内容档（4–7 / 7–12 / 13–16 / 17+）× 领域（自拼 / 高频词 / 绘本 / 口语 / 商务）。
- `/parent/settings` 改成「学习偏好」而非「使用限制」：可调每天目标时长、免打扰时段。
  **不拦截、不强制休息**，只是提示与建议。

## 9. 动效：三条主序列

原则：**只在需要理解「发生了什么」的地方动，不为好看而动。** 全部尊重 `prefers-reduced-motion`。

1. **地图进场**（`/learn`、首页切片）：白底路面描画 0.95s → 绿色段 0.78s 铺到当前关 →
   已完成关的勾按 0.66 / 0.81 / 0.96s 依次盖章 → 当前关 0.90s 落下，到底时压扁 7% 再回弹，
   脚下同时荡开一圈白尘（全场唯一「重」的一下，和盖章是同一套手感）→
   未来路段 0.92s 起淡入、终点旗 1.18s 落位 → 教练与奖励条 1.15s 进场。
   常驻：当前节点光环 3.6s 呼吸 + 教练 4.6s 上下浮——孩子等待的那几秒不是死图。
   *这就是「今天从哪继续」的答案，不是装饰。*
2. **答题反馈**（`/learn/unit`）：答对 = 卡片放大 1.04 → 回弹 + 对勾盖章 + 音效；
   答错 = 水平抖动 3 次 + 提示文字淡入。**不做扣分动画。**
3. **结算推进**（`/learn/unit/:id/done` → `/learn`）：三颗星依次落下 → 地图上当前节点
   从「第 4 关」向「第 5 关」移动一格并放大成为新的当前关。全产品唯一的「进度感」来源。

按钮反馈：hover 抬 3px、press 下沉 3px、focus 保留 4px 阳光黄描边。同一属性只由一个系统控制。

## 13. 验收口径

- 每个页面在 **1440×900 与 390×844** 两张截图下都要能过（原型已建立这个标准）。
- 学习端所有可点元素 ≥ 64px；监护端表单键盘可达、错误不丢焦点。
