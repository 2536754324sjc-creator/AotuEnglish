# Clarify Feedback Before Choosing a Revision

Load this guide when the user requests clarification, or feedback or uncertainty discovered during frontend work leaves materially different plausible revisions. Repeated overall rejection with an unresolved cause calls for this route before another full concept build or delegation, not an automatic long questionnaire. Work from the actual brief and available artifact; no development conversation or companion Skill is required.

## Route once, then keep designing

When `clear-feedback` is available, use it with this guide's scope and return criteria in one conversation, not two passes. Otherwise use this guide directly; no installation, special question tool, or network request is required. Do not claim the companion ran when only this fallback was used. UI Done continues to own design, required capabilities, implementation and verification.

Honor the user's **current** requested depth and pace. An explicit in-depth interview warrants prerequisite-aware follow-ups; it is not permanent authorization to interview after the user asks to see drafts, delegate taste decisions, or stop. Conversely, do not silently abandon a requested clarification-first stage to build another application. Neither clarification nor a liked reference authorizes a rewrite, integration or deployment.

## Decide whether an answer is actually needed

Inspect the available artifact, affected action, confirmed requirements and selected references first. Separate observable defects, the user's reported feeling, and your causal hypothesis. If a screenshot or dynamic state is unavailable, name that limit rather than inventing observations.

- **Specific instruction or reproducible fault:** investigate or correct it within authorization. Covered text or a button that cannot save does not require a taste interview.
- **Consequential uncertainty:** identify the two plausible revisions and the missing distinction that changes which one you would make. Diagnose measurable failures first; ask only about the remaining preference.
- **Enough context for a reversible comparison:** use a focused visual comparison to resolve the uncertainty within the authorized scope. If the user has requested drafts or delegated the open taste choice, proceed under explicit assumptions without asking for that permission again. Prior references or a bare “continue” do not override an unresolved clarification-first request.
- **Mixed feedback:** fix confirmed defects while clarifying the uncertain direction. A taste question must not block unrelated repairs; a technical fix does not resolve a taste complaint.
- **User stops:** stop the requested iteration. Preserve unresolved dissatisfaction and the stopping reason; do not seek one more answer or interpret exhaustion as approval.

Do not repeat answered preferences or require library names, CSS values, or professional design decisions. If answers conflict, name the specific conflict rather than quietly discarding an earlier constraint.

## Choose the next useful comparison, not the next question by habit

Before another round, identify what the last answer changed and what the next answer will change. If neither is concrete, synthesize what is known and change the method rather than rephrase the same question. This is an information-gain check, not a fixed round quota or permission to claim understanding prematurely.

Ask about recognizable results using the current screen, an action or comparable examples. Group independent questions or references when they are easier to judge together; use one-at-a-time questions when an answer genuinely determines the next branch. Give a design recommendation with its basis, but do not recommend how the user should feel. Allow combinations, rejection of every option, and “I cannot describe it.”

For an in-depth interview, keep a compact map of confirmed decisions, consequential open branches and dependencies. Use existing product facts; do not invent an exhaustive specification. After each answer, update the affected branches rather than restart the survey. Workflow answers establish constraints, not visual agreement. A request for design cannot be completed by learning the workflow alone.

Distinguish a **scope answer** from a **direction answer**. “Both appearance and information organization,” “desktop only,” and “keep simultaneous comparison” tell you what must change or survive; they do not choose typography, surface character, spatial relationships or motion. After repeated overall rejection, name what is still open and ask the next consequential question or use an explicitly authorized visual comparison. Do not mark clarification complete because the user selected the broadest option in one question. A useful next prompt points to actual evidence: “In these viewed examples, is it the compact typographic hierarchy, the continuous data surface, or neither that you want to explore? I recommend … because …”. Do not invent examples or assert that these are the user's only options.

When the answer is needed, ask and end the turn. Do not use an asynchronous question as a notification while independently implementing one possible answer. If the user cannot judge from words, show a small reference-led study at the [current choice checkpoint](layered-design-selection.md#choice-checkpoints), not another nearly complete application. Keep following the unresolved distinction until the user confirms the concrete interpretation or explicitly delegates/requests drafts; there is no fixed interview length.

When words stop distinguishing outcomes, use a small, professionally developed **batch** of numbered visual alternatives with the same representative content, viewing scale, and ordinary action state. Compare actual combinations of typography, icons, spacing, surfaces and controls; do not ask the user to evaluate “round corners” in isolation. A motion question needs an accessible normal-speed previsualization, not only stills. Do not deliberately weaken an option to make your preferred one win. Reuse relevant selected references instead of sending the user through an endless sequence of unrelated screenshots.

New pages and substantial redesigns default to [progressive design and layered selection](layered-design-selection.md): compare the unsettled aspect in context, then refine one integrated key-page sample before expanding the full implementation. Structure, type, data and important motion can be explored together; a selected skeleton is not approval of unseen components. Bounded playable samples may use real React/UI/chart/GSAP code within the authorized prototype scope without rebuilding business APIs, persistence or switching the normal entry. Do not restart settled layers or demand verbal certainty about qualities that must be seen. A design choice, approval of a draft, and acceptance of its implementation remain distinct.

Keep evaluation axes separate when the user's feedback distinguishes them: attractiveness, recognizable design character, perceived generic/AI-like appearance, and ease of use can disagree. “Not AI-like” does not mean “beautiful”; “AI-like is acceptable” does not waive design quality. A preference for rich icon/label combinations does not authorize arbitrary decoration, game controls or new features.

Method basis: [GRILL-ME's prerequisite-aware method](https://github.com/mattpocock/skills/blob/d81f3a183412e71a5b1e84ca21bc1a35eea03a60/skills/productivity/grilling/SKILL.md) and [usage guidance](https://github.com/mattpocock/skills/blob/d81f3a183412e71a5b1e84ca21bc1a35eea03a60/docs/productivity/grill-me.md). This adaptation retains dependent follow-ups and confirmation, while choosing conversation or visual comparison from the current task and permission. It does not require that external Skill.

## Return according to the decision actually made

Retain a short brief in the existing task context: objective, decisive original wording, rejected and retained qualities, exact selected reference/state and caveat, proposed change, remaining assumptions, and the ordinary action that will reveal it. Apply the [concrete-reference method](open-source-ui-sources.md#preserve-concrete-reference-evidence). Separate confirmed preferences, observed traits and proposed adaptations; no new dossier or permanent preference file is required.

- **Understanding confirmed:** restate the concrete intended result, retained boundaries and consequential transfer choices in ordinary language. The user's confirmation closes those distinctions; it does not approve an unseen design or every future detail. If a consequential distinction is still unresolved, do not label it understood.
- **Comparison or taste delegation authorized:** state the open assumptions and deliver the bounded drafts or previsualization requested. This is a valid stage exit, not complete understanding or final acceptance. Do not keep an earlier interview mandate alive against a later explicit instruction to show alternatives. Return to only the distinctions the resulting feedback leaves unresolved.
- **Implementation authorized:** follow `../SKILL.md` and the [integrated-sample boundary](layered-design-selection.md#build-one-integrated-key-page-sample). Agreement on adjectives, a workflow, or one animation does not approve an entire application. Feasibility and presentational code may support an authorized isolated comparison before full design confirmation; label simulation and keep that work separate from business features, persistence and the normal entry. After the representative experience is confirmed, implement only the agreed scope; applicable prior designs or explicitly delegated decisions need not be reconfirmed.
- **Stopped without acceptance:** retain that status and cease the UI iteration. No automatic integration, new trial, or success claim follows from “leave it there.”

Preserve the user's clarification-first request, subsequent changes to that request, confirmed answers and unresolved assumptions in an authorized handoff. Do not turn a project preference into a universal rule. If the next result is rejected, investigate that remaining difference rather than defend library coverage.

## Worked examples

**“动画还是没有高级感.”** If inspection shows only panel fades and list scrolling, distinguish barely perceptible change, discontinuity, unrelated movements, and dissatisfaction with the whole layout. Fix an observed snap directly. For “每个部分各动各的,” compare coordinated selection → contextual editing → completion using the [motion sequence method](motion-scroll-and-3d.md#design-a-sequence-not-a-tween-quota), not longer fades. If the layout itself is rejected, use the [composition method](page-composition.md#repair-a-rejected-layout-family).

**“分区清楚，但不要割裂.”** Retain both requirements. Compare the same populated work state with clear local surfaces and shared alignment/type/action relationships. Removing all boundaries answers only half the brief; giving every region identical framing can fail it too. Neither rectangles nor cards are automatically the defect.

**“我说不清，先给我几稿.”** When this explicitly changes an earlier interview request, use known constraints to show coherent alternatives, stating unresolved taste assumptions. Do not continue asking for design vocabulary or claim that permission to compare is design approval. Refine and confirm the representative design before full implementation.

**“外观和布局都要重做，用新版再来.”** This rejects both aspects; it does not say which replacement looks right. Recover the actual rejected artifacts and any retained preference. Ask the remaining visual distinction with concrete references, then develop the selected study; if the user instead explicitly requests a batch or delegates the choice, follow that request. Do not silently translate this scope answer into “a pale list versus dark cards” or treat a past “B is better” as current approval after B was rejected.

**“这个标题被挡住了，移开图标.”** Inspect and repair the overlap and its affected state. A prior broad design complaint does not turn this explicit correction into another interview.

**“一般，但没时间再改了.”** Record a usable candidate only if usability was checked, and separately record unmet design expectations and the user's decision to stop. Do not request another comparison, switch the normal entry, or present the case as a design success.
